02 / 14
Copiloto de Inteligencia Metodológica

La evolución de nuestro marco actual, apoyado en el mismo contenido, pero estructurado de forma navegable, intuitiva, guiada y ahora potenciado por IA.

📚
Contenido curado
Módulos metodológicos en Markdown con anotaciones semánticas para búsqueda precisa y routing contextual.
🧭
Guía de decisión
Árboles determinísticos que guían al consultor paso a paso sin ambigüedad. Trazables y auditables.
🤖
IA como capa adicional
El LLM agrega valor cuando el contenido no alcanza — nunca reemplaza la estructura. Consume responsablemente.
📊
Aprendizaje continuo
Feedback de consultores alimenta una case library que enriquece futuras respuestas y mejora el routing.
El Copiloto no reemplaza nuestro criterio, lo potencia con estructura y contexto.

Funcionalidades

Interfaz interactiva que permite explorar el conocimiento, ejecutar decisiones y analizar escenarios con apoyo de lenguaje natural.

🗂️
Exploración del Conocimiento
Navegación modular con key topics interactivos. El usuario explora el marco metodológico como una experiencia guiada, no un documento estático.
🌳
Árboles de Decisión
Evaluación guiada de escenarios, determinística y trazable. Cada hoja del árbol tiene una decisión clara con post-actions configurables.
🤖
Copiloto de Análisis
Interpreta contexto técnico, genera recomendaciones, explica decisiones. Activado solo cuando el contenido estructurado no alcanza.
📄
Integración Documental
Conecta con SAP Help, Notas SAP, SharePoint y PPTs. Los assets técnicos están registrados en intent_assets del frontmatter de cada módulo.
Arquitectura Técnica
04 / 14
Arquitectura de Módulos

Adopción adecuada · Separación de responsabilidades. Cada capa tiene un rol claro — no mezclar lógica entre módulos.

webapp/main.py Orquestador FastAPI
Punto de entrada (uvicorn). Rutas SSR de módulos, endpoints HTMX (wizard, análisis, asistente), auth y assets. Reemplaza al viejo bootstrap Streamlit.
webapp/templates · static Presentación (SSR)
Jinja2 server-side + HTMX (hipermedia, partials que se swapean sin recargar) + Alpine.js (estado liviano) + Tailwind. Solo renderiza.
webapp/services/ Lógica de aplicación
content_service (parser Markdown) · wizard_service (árboles) · section_analysis + assistant (LLM) · auth_service (MSAL) · case_library.
core/ Dominio puro Danwor
content_registry · prompts · routing_scorers · corpus · content_metadata · utils. Sin acoplamiento a UI ni a Streamlit (6 módulos).
content_packs/ Datos y configuración
Por pack (datasphere_mvp, bdc_next): content/*.md · trees/*.yaml · assets/ · templates/. Única fuente de verdad, con herencia entre packs. Editable sin tocar Python.
⚠️ No modificar sin revisión cross-módulo: core/content_registry.py · webapp/services/content_service.py · webapp/static/tools.css

Cómo se ejecuta el pipeline
✅Determinístico y server-side: el scoring (routing_scorers) y el match de árboles/assets resuelven antes que el LLM. El LLM es el último recurso.
⚡Cada paso devuelve un fragmento HTMX que se inserta sin recargar. El LLM (API Real) es lo único con costo y solo se activa al final del flujo.
💡El modo Simulación (DANWOR_EXECUTION_MODE) permite recorrer todo el flujo sin consumir créditos — muestra el prompt que se enviaría.

07 / 14
Integración LLM

Capas & Responsabilidades. El LLM es una capa adicional — no la fuente primaria de respuestas.

SectionAnalysisService · AssistantChatService webapp/services/
Llaman a OpenAI directamente (cliente openai, modelo de config.MODEL). La concurrencia la maneja FastAPI — sin singleton ni threads manuales. Respuesta renderizada a HTML (markdown).
build_system_prompt · build_topic_prompt core/prompts.py
Construyen el prompt con el contexto del módulo activo, scope, acción solicitada y casos reales de la case_library/.
DANWOR_EXECUTION_MODE config.py / entorno
Modo Simulación vs API Real, leído por variable de entorno (no por session_state). El asistente del routing usa routing_scorers antes de tocar el LLM.
IA_ENABLED_MODULES config.py
Módulos con IA habilitada (ia_enabled_for()). Controla si se muestra el panel de acciones de sección por módulo (p. ej. 00 Intro queda sin panel).
💡 Modo Simulación: no se consumen créditos — el output muestra el prompt que se enviaría. Útil para desarrollo y validación sin costo.
Seguridad
08 / 14
Seguridad y Gobernanza

Microsoft 365 autentica usuarios, pero no neutraliza archivos ni contenido malicioso. El copiloto separa identidad, autorización, parsing seguro y guardrails LLM.

🔐
Identidad
Microsoft Entra ID por OAuth2 + PKCE (public client). El id_token se valida server-side contra el JWKS del tenant (firma RS256, audience, issuer) + allow-list por dominio. Sesión en cookie HttpOnly firmada (JWT); rutas protegidas.
📁
Archivos seguros
No ejecuta .py. YAML con safe_load. Markdown como texto/contenido no confiable.
🤖
LLM Safety
Documentos son contexto, no instrucciones. No expone secrets ni variables de entorno al modelo.
📋
Operación
Logs sin tokens. Feedback/casos tratados como datos internos. Rate limit básico como control evolutivo.
🛡️ OWASP: upload irrestricto solo si se habilita en el futuro, con allowlist, tamaño, renombre y storage aislado.
Archivos Markdown
09 / 14
Estructura del Contenido

Anatomía de un módulo .md. Cada archivo markdown sigue una estructura canónica con frontmatter YAML, headings numerados y marcadores custom.

Anatomía del módulo
--- module: M03 title: "Integración Datasphere" key_topics: [extraccion, replicacion] scope: # qué cubre el módulo intent_assets: # templates descargables out_of_scope_redirect: # redireccionamiento --- ## Heading # IDs auto via SECTION_NUMBER_WIDTH {{section_meta}} # señales de routing {{semantic_summary}} # contexto invisible IA {{callout}} # marcadores renderizados {{tree_button}} # launcher de árbol {{support: Pin=true}} # botón pinner
Reglas de contenido
✅section_meta es el mecanismo principal de routing — documentar bien las keywords cubre el 90% de los casos.
✅intent_assets en el frontmatter para templates descargables (.abap, .sql, .yaml).
✅Los headings generan anchors automáticos; la numeración visible es presentación, no identidad semántica.
⚠️section_exclude usarlo con moderación — indica keywords que se solapan.
🚫Nivel 2 (texto libre) deshabilitado — generaba falsos positivos. No reactivar sin umbral ≥ 4 y validación.

Árboles de Decisión

Estructura canónica de los archivos .yaml. Cada árbol define un flujo determinístico con nodos, hojas y tipos de salida.

Estructura canónica
CampoEjemploDescripción

Tipos de Salida (post_actions.mode)
✅
Resuelto [resolved]
Decisión tomada. El árbol resuelve el caso completo sin necesitar LLM.
💡
Valor LLM [llm_value_add]
El árbol sugiere pero el LLM puede profundizar vía botón Analizar.
⚠️
Requiere Intervención [needs_human_review]
Requiere validación humana. El árbol no puede decidir solo.
Los casos completados se guardan en case_library/ — base de conocimiento para enriquecer los prompts del LLM.

11 / 14
Patrones críticos de FastAPI / HTMX

Patrones que se deben conocer en la arquitectura SSR. El render es server-side; HTMX intercambia fragmentos y Alpine maneja el estado liviano del cliente.

⚠️Tema sin flash (FOUC) en navegación SSR
Cada navegación es un load completo. El tema se aplica con un script síncrono en el <head> (lee la cookie y setea la clase en <html>) ANTES del primer paint. Alpine solo conmuta. Si se delega solo a Alpine, parpadea oscuro→claro.
⚠️x-cloak en elementos x-show
Sin x-cloak, los x-show (tabs, íconos) se ven un instante antes de que Alpine los oculte. Regla [x-cloak]{display:none} + el atributo en cada elemento condicional.
✅HTMX: fragmentos, no recargas
Wizard, análisis de sección y asistente usan hx-post + hx-target + hx-swap: el server devuelve un partial Jinja que se inserta sin recargar la página.
✅Render cacheado + resolución pack-pura
load_module con @lru_cache (documento inmutable) evita re-parsear Markdown por request. content_registry resuelve solo desde content_packs/ (con herencia), sin fallback a carpetas raíz.

Guía de Modificaciones

Qué tocar y qué no. Separación clara entre archivos seguros de editar y componentes que requieren revisión de impacto.

✅ SEGURO modificar
📝
content_packs/<pack>/content/*.md
Agregar secciones, section_meta, callouts, intent_assets. No cambiar la estructura del frontmatter.
🌳
content_packs/<pack>/trees/*.yaml
Nuevos árboles o ramas. Respetar el schema: id, start, nodes, leaves, links (module por stem exacto).
⚙️
config.py
IA_ENABLED_MODULES, MODEL, ALLOWED_USERS, DANWOR_EXECUTION_MODE, SESSION_SECRET.
📁
content_packs/<pack>/assets · templates
Embeds HTML y templates descargables. Registrar en intent_assets del .md correspondiente.
🎨
webapp/static/*.css
app · content · layout · tools. Verificar que no rompan tiles, tema claro/oscuro ni el render de secciones.
⚠️ Revisar impacto antes de tocar
🔑
core/content_registry.py
Resolución de packs y herencia. Un cambio afecta cómo resuelven TODOS los módulos, árboles y assets.
📄
webapp/services/content_service.py
Parser Markdown (regex de markers + render). Validar contra todos los módulos; está cacheado (lru_cache).
🌳
webapp/services/wizard_service.py
Match de árbol por links.module = stem exacto. No volver al match por prefijo numérico (cruzaba packs).
🔐
webapp/main.py — gate de sesión
Las rutas SSR exigen cookie de sesión válida; show_panel depende de IA/diagnóstico. Probar entrada/redirect.
🎨
webapp/static/tools.css
Carga última → gana la cascada. Concentra tiles, tema claro/oscuro y scrollbars; revisar al tocar estilos.

How-to Git · deployment → main

Dos ramas con responsabilidades claras: deployment para desarrollo y pruebas, main como versión productiva estable. DigitalOcean apunta a main y redeploya solo cuando promovemos cambios.

deployment
desarrollo / pruebas / cambios nuevos
→
main
versión productiva / estable
→
DigitalOcean
redeploy automático al detectar cambios en main
1
Sincronizar y trabajar sobre deployment
# Cambiar a la rama de desarrollo
git fetch origin
git checkout deployment
git pull origin deployment
# Verificar rama actual
git branch
# Debe verse:
* deployment
main
# Confirmar estado limpio antes de tocar
git status
✅ Qué esperar: Already up to date y working tree clean. Si hay archivos modificados, revisar antes de empezar.
2
Hacer cambios y validar localmente
# Probar localmente (FastAPI/uvicorn, puerto 8501)
python -m uvicorn webapp.main:app --reload --port 8501
# Una vez validado
git status
git add .
git commit -m "Descripción breve del cambio"
git push origin deployment
✅ Qué esperar: el push actualiza origin/deployment, pero no redeploya producción. Warnings de CRLF/LF son normales en Windows si no cambian el contenido real.
4
Verificar que main y deployment estén iguales
# Actualizar referencias remotas
git fetch origin
# Comparar contenido (vacío = mismo código)
git diff origin/main origin/deployment
# Comparar commits pendientes (vacío = misma historia)
git log --oneline origin/main..origin/deployment
git log --oneline origin/deployment..origin/main
# Resumen de ramas y commits
git branch -vv
Si diff no devuelve nada, el contenido está alineado. Si además ambos log están vacíos, también comparten historia.
⚠️ Qué esperar: puede haber commits distintos aunque diff esté vacío. Eso no es un problema funcional; solo indica historia Git diferente.
3
Promover cambios estables a main
# Cambiar a main
git checkout main
# Actualizar main local
git fetch origin
git pull origin main
# Mergear lo ya subido a deployment
git merge origin/deployment -m "Merge deployment changes into main"
# Subir main actualizado → redeploy
git push origin main
✅ DigitalOcean detecta el push a main y redeploya automáticamente.
⚠️ Qué esperar: si aparece conflicto, resolver archivos marcados con UU, luego git add, git commit y recién después git push origin main.
5
Caso especial · realinear ramas
Si diff está vacío pero los hashes difieren, no hace falta hacer nada. Usar esto solo si se decide que main debe quedar idéntica a deployment también en historia.
# Requiere decisión explícita: reescribe main remoto
git checkout main
git reset --hard origin/deployment
git push origin main --force-with-lease
⚠️ No es el camino normal. Para promoción estándar, usar merge desde origin/deployment.
⛔ Qué esperar: este paso reescribe la historia de main. No usarlo para resolver conflictos comunes de merge.
6
Configuración DigitalOcean
App → Settings / Components → Source
Repository: DanworForBusiness/copiloto-metodologico
Branch: main
Autodeploy: enabled
push a deployment → no impacta producción
push a main → redeploy productivo automático
✅ Qué esperar: luego del push a main, DigitalOcean inicia build/deploy. Variables de entorno no viajan por Git: se administran en App Platform.
