Arquitectura y conceptos

La misma planta, ahora con el dato

Ya sabemos cómo funciona una planta potabilizadora: capta el agua, la trata, la distribuye. Datasphere hace lo mismo con el dato, en cuatro pasos — no un checklist rígido, sino la estructura que sostiene la trazabilidad, el linaje y el gobierno del dato.

1 · Ingesta

El agua tal cual llega

El dato, tal cual sale del sistema origen.

+ tocá para ver más
A veces ya viene potable: el origen entrega estructura y semántica resueltas, como una fuente que nace pura. Ahí el contrato ya estaba resuelto antes de llegar — Datasphere lo hereda, no lo inventa.
→
2 · Armonización

El tratamiento, cuando hace falta

Limpia, estandariza, arma el contrato.

+ tocá para ver más
Si el origen solo entrega agua bruta —una extracción robusta, sin más— acá se resuelve el contrato de punta a punta. Cuanto más cerca del origen, mejor: esto es la red de contención, no el lugar por defecto.
→
3 · Publicación

Lista para la canilla

El Data Product, listo para consumo.

+ tocá para ver más
La materialización del contrato: gobernada, reutilizable, orientada a un consumidor de negocio puntual — el mismo concepto de Data Product de todo el recorrido.
↕ Gobierno Semántico — corre por debajo de los tres pasos, todo el tiempo: el mismo diccionario de reglas (qué es "Cliente", qué significa "Venta") para que todos hablen el mismo idioma.

Postura DanworPostura recomendada

La complejidad del contrato dicta dónde conviene resolverlo:

  • Baja complejidad: se resuelve en origen
  • Complejidad media: parcial en origen, completado en la Armonización
  • Alta complejidad: destino, la Armonización resuelve todo

Nunca al revés: no se elige dónde resolver el contrato por comodidad, sino por cuánto puede realmente entregar el origen.

Siguiendo la analogía Data Mesh, donde cada provincia gestiona su propio tramo del río: son los Espacios en Datasphere el correspondiente a cada dominio: no es una carpeta, es una jurisdicción con sus propios recursos, seguridad y ciclo de vida. Y quién puede acceder a ese tramo se decide con roles como primera cerradura, incluso antes de suplementar con seguridad a nivel de fila (DAC) que veremos en el Tema 3.

Data Builder — objetos core

Hechos, dimensiones y el vocabulario del modelado

Datasphere ofrece distintos artefactos: Tablas locales y remotas, Graphical Views vs. SQL Views — pero lo que realmente define el valor del objeto para consumo es su tipo y uso semántico: qué es, y qué rol cumple.

Dimension

Los maestros

Cliente, Producto, Centro de Costo — con clave única.

+ tocá para ver más
Atributos descriptivos de una entidad de negocio. Se asocia con Facts en el modelo analítico — sin dimensiones, un hecho no tiene con qué cruzarse.
+
Fact

Los hechos

Ventas, Pedidos, Stock — lo que se mide.

+ tocá para ver más
Hechos transaccionales, con métricas y asociaciones a dimensiones. El corazón de cualquier modelo analítico.
=
Modelo Analítico

Lo que se consume

Combina Facts y Dimensions en un objeto final.

+ tocá para ver más
La base para reportes en SAC o Power BI: ya no es un objeto técnico, es el data product listo para el negocio.
Relacional, Text, Hierarchy — tipos de apoyo: preparación, textos multi-idioma y jerarquías, siempre asociados a una Dimension o Fact.
Una Fact Table (Tabla de hecho) no sirve sola: necesita Dimensiones (Cliente, Producto, Tiempo) para poder cruzarse, y métricas que digan qué se está midiendo. Es la misma lógica que la norma de potabilidad del recorrido anterior — una especificación que tiene que cumplirse antes de que el dato sea confiable para reporting.

Postura DanworPostura recomendada

La convención de nombres codifica la capa en el propio objeto:

  • Patrón: <Capa><Artefacto><Variante>_<Origen>_<libre>
  • Ejemplo: 2VD_CLIENTES_CABECERA → Capa 2 (armonización) · Vista · Dimensión

La capa 1 mantiene el dato crudo; si hay renombrado, joins o limpieza, ya no es Capa 1.

Controles y capa analítica

Quién ve qué, y cómo.

Data Access Control (DAC) resuelve seguridad a nivel fila y columna. La estructura que elijas depende de cómo se organiza el acceso en el cliente — no hay una única respuesta correcta.

Valores Individuales

El más simple

Asignación fija por usuario (ej: SalesOrg = AR01).

+ tocá para ver más
Ideal para PoC y MVP: accesos estáticos, de baja frecuencia de cambio. El punto de partida más seguro y auditable.
→
Operadores y Valores

Con lógica condicional

Rangos, "mayor que", combinaciones.

+ tocá para ver más
Para accesos con lógica de negocio: períodos, montos, umbrales — cuando un valor fijo no alcanza.
→
Jerarquía

El más potente

El acceso se hereda por niveles.

+ tocá para ver más
El nodo padre da acceso a todos sus descendientes — ideal para estructuras organizacionales (organigrama, centros de costo).

Principio DanworPrincipio recomendado

La seguridad bien diseñada no debería retrasar al negocio, sino garantizar que los datos sean un activo confiable. El modelo de seguridad no es un paso posterior al modelado — se deriva del diseño de dominios y data products definidos a nivel conceptual.

Flujos de datos

Movimiento del dato

Data Flows, Transformation Flows, Replication Flows: tres mecanismos, una misma decisión de fondo: federar, persistir, o aterrizar en Object Store.

Federación

Tablas remotas

Acceso en tiempo real, sin mover el dato.

+ tocá para ver más
Depende de la latencia y disponibilidad del origen. Rol: acceso al dato.
→
Persistencia

Tablas locales

Vía flujos o replicación.

+ tocá para ver más
Alto volumen, múltiples fuentes combinadas. Rol: construcción del Data Product.
→
Object Store (HDLF)

Archivos, no tablas

Parquet + transaction log.

+ tocá para ver más
Históricos masivos, medallion Bronze/Silver/Gold. Rol: Lakehouse / aterrizaje BDC-ready.

Regla práctica DanworRegla práctica recomendada

Federá por defecto: los datos siempre actualizados, sin redundancia. Persistí cuando el volumen es alto, la transformación es costosa, o la performance en la herramienta de consumo lo exige. La pregunta de fondo nunca es "federación o persistencia" — es cuándo materializar.

Tema 5 de 5

Integración de datos

El momento en que el dato cambia de dueño

Ya vimos cómo la planta capta el agua (Ingesta, Tema 1). Pero, ¿por dónde entra exactamente? Siempre por una toma de agua construida y acordada — nunca metiendo un caño donde se nos ocurra.

Una API es una toma de agua: un punto de conexión fijo y regulado entre la fuente y la planta. Un extractor (ODP-SAPI, ODP-CDS) es una toma que el propio origen ya construyó y mantiene — vos solo te conectás. La tabla base no tiene toma: es meter un caño directo en el río. Si el cauce cambia —un upgrade de SAP— tu caño puede quedar en tierra seca.
API funcional SAP

Propiedad de SAP

La toma que ya construyó el origen.

+ tocá para ver más
Es la API que SAP mantiene y actualiza — no se toca, se consume tal cual viene liberada.
→
API Corporativa

Propiedad del cliente

Tu propia toma, entre el río y tu planta.

+ tocá para ver más
El momento en que el dato pasa de pertenecer a SAP a pertenecer al cliente — con ownership, versionado y SLA propios.
Si cada consumidor le pide directo a la toma de SAP, un cambio río arriba los golpea a todos al mismo tiempo. Si en cambio todos piden en tu propia toma —y sos vos quien conecta con la de SAP— el cambio lo absorbés una sola vez, en un solo lugar, y es transparente para los demás.

Guardrail DanworPunto de atención

La extracción directa de tablas base no es una recomendación — nunca es el contrato. Siempre a través de fuentes autorizadas:

  • ODP-SAPI o ODP-CDS
  • CDS Views habilitadas para extracción (@Analytics.dataExtraction.enabled)

Es la diferencia entre consumir una API liberada y comprometer gobernanza, estabilidad y upgrades futuros.

Referencia técnica

Desde ABAP 7.55 existen dos generaciones de vistas CDS, y si bien es la evolución natural de SAP, hay consideraciones importantes de cara a la extracción y framework ODP.

Semántica del negocio

La toma no es la norma

Acabamos de construir nuestra propia toma de agua — la API corporativa. Pero ojo: tener la toma no es tener el contrato. La toma define por dónde entra el agua y quién controla esa entrada; la norma define qué tiene que cumplir esa agua para que cualquiera la consuma sin volver a analizarla.

Toma certificada

El agua llega con su análisis completo

El contrato quedó resuelto en origen.

+ tocá para ver más
Nombres, tipos, dominios y reglas ya estandarizados a nivel de la API corporativa. Datasphere hereda el contrato — no lo inventa.
↔
Toma sin certificar

Agua buena, pero sin certificado

El contrato en origen es parcial.

+ tocá para ver más
La toma funciona perfecto, pero cada fuente habla su propio idioma. Lo que falte del contrato lo completa la planta, en la Armonización — el criterio de complejidad del Tema 1.
¿Y qué certifica la norma, además de la calidad? El idioma. Que "turbidez" se mida igual en todas las plantas, que "potable" signifique lo mismo en toda la red. En datos, eso es la semántica del negocio: mismos nombres, mismos tipos, mismos dominios para las mismas cosas — el diccionario del Gobierno Semántico que corre por debajo de todo el recorrido.

Postura DanworPostura recomendada

Por eso en los proyectos la pregunta se hace así: ¿la semántica de negocio está completamente resuelta a nivel de la API corporativa de extracción? Si la respuesta no es un sí rotundo, el contrato en origen se considera parcial y se completa en la capa de Armonización.
